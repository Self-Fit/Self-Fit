# Self Fit API contract

Base `/api`; backend local port `4000`. JSON request/response unless a file is described. Session authentication uses an HttpOnly cookie; fetch with `credentials: 'include'`. Mutation requests require the same origin (local frontend origin configured by `APP_ORIGIN`). Errors: `{error:{code,message,details?}}`. A U+0000 character anywhere in the address or JSON body, or a malformed percent-encoded path segment, is `400 INVALID_INPUT` (PostgreSQL text cannot store U+0000). Dates never use year 0000. Success objects are described below, not wrapped in `data`. All activity dates are Korea `YYYY-MM-DD`; timestamps are ISO instants. No client date override exists.

`User = {id,role:'student'|'teacher',studentNumber,name,grade,classNumber,targetType:'required'|'optional'|null,fitnessGrade:null|1|2|3|4|5,fitnessGradeYear:null|number,fitnessGradeSemester:null|2,participating:boolean|null,mustChangePassword,lastLoginAt:null|ISO,createdAt:ISO}`. `grade` is the school year; `fitnessGrade` is the latest confirmed second-semester fitness grade, with all three fitness fields null when unavailable. Fitness grades do not alter targetType or membership. `participating` means "active in the challenge this response is about"; the account column was dropped (migration `20261021090000_drop_user_participating`), so account-level responses such as `/auth/me` report `null`.

Roster queries and roster/record export filters accept `fitnessGrade=1|2|3|4|5|unmeasured`; omission selects every grade. Student detail additionally returns `fitnessHistory:[{year,semester,grade,score}]`, newest year/semester first. Semester is 1 or 2, grade is 1–5, score is numeric or null. Reimports of one school year/semester validate the existing assessment rather than inventing another semester; conflicting values stop the import for explicit reconciliation. Source provenance is retained privately. Imports update existing matched student accounts without changing credentials, participation, or exercise records.
`Record = {id,date,value,version,attachments:[{id,name,kind,size,url}],history,updatedAt}`. Teacher student-detail records include `history:[{id,beforeValue,afterValue,reason,createdAt,actorId,source}]`.
Values: walking integer band `0..5`; check boolean; counts nonnegative safe integer; distance finite nonnegative number. Dumbbell values have exactly the keys in the selected week's `exercises[].id`, each holding a nonnegative safe-integer set count or null. At least one exercise must be non-null. A day is achieved only when every exercise reaches its own `targetSets`; `weeklyTarget` achieved days complete that week. The legacy 2026 challenge retains `{D12_CURL:number|null,D12_SQUAT:number|null,D12_ROW:number|null}`, ten repetitions × two sets per exercise and three achieved days during 2026-08-31–09-04. Missing values remain missing, never 0. Extra sets cannot compensate for another exercise or day.

## Authentication

- `POST /auth/login {studentNumber,password}` → `{user}`. Teacher uses its configured account identifier in studentNumber. A successful account switch revokes the previous account's push binding for this browser device, including after its session expired. Failed attempts are limited to 10 per account and 300 per client address in 15 minutes (429 `RATE_LIMITED`); successful logins do not count. Set `TRUST_PROXY` behind a reverse proxy.
- `GET /auth/me` → `{user}`. 401 when unauthenticated.
- `POST /auth/logout {pushEndpoint?}` → `{ok:true}`. Revokes the browser device identified by its opaque device cookie or its session's saved device binding, atomically with its session. Provider lookup is unnecessary, and other devices are preserved. The optional explicit endpoint is revoked only when owned by the authenticated account. Anonymous or expired-session logout may revoke the device identified by its valid device cookie, but cannot revoke an arbitrary explicit endpoint.
- `POST /auth/change-password {currentPassword?,newPassword}` → `{user}`. 8–128 characters including English letters and digits, must differ from student number. `currentPassword` is optional only for authenticated first-login temporary-password sessions. First-login accounts can only use auth endpoints until changed.
- `GET /health` → database readiness only; no account details.

## Challenges

The authoritative challenge types, validation rules, requests, response fixtures and error codes are in [the challenge API contract](../docs/challenges/api-contract.md) and [shared JSON fixtures](../docs/challenges/fixtures/). The backend provides teacher challenge collection/detail, create, patch, duplicate, publish, archive and draft-delete endpoints, membership selection/registration/invitations, and student invitation and challenge-specific record endpoints. Frontend screens and final UI integration are separate phases.

A challenge contains its own ordered weeks, activity dates and memberships. Lifecycle is `draft → published → archived`; `phase` is computed from the server's Korean date as `draft|upcoming|active|rest|ended|archived`. Only a draft may be deleted. Week structure and dates are editable while draft or before the published start date; once started, only title, description and color may change. Duplicating creates a draft with shifted dates and retained rest gaps, without copying participants or records.

Legacy paths resolve the current challenge on each request:

- Teacher: the published challenge in progress first — phase `active`, then `rest`, then the earliest `upcoming`, then the most recently `ended` (ties: latest `startDate`). An explicit `challengeId` query selects another existing challenge, including draft/archived for teacher review. `GET /teacher/challenges` returns this as `currentId`.
- Student: an active membership in a published challenge, preferring phase `active`, then `upcoming`, then `rest`, otherwise the most recently ended challenge. No match yields no current challenge. `GET /program` returns `404 CHALLENGE_NOT_FOUND`; legacy student reads retain their empty nonparticipant response (dashboard `program:null`, empty records and a zero-week summary; single-date record `null`).

`GET /teacher/overview`, `/teacher/participation`, `/teacher/export`, `/teacher/corrections`, `/teacher/students/:id` accept `challengeId`; the correction audit export also accepts it. JSON responses from these scoped reads include `challenge: ChallengeSummary`. Exports remain XLSX files and use only the selected challenge's weeks and records. Performance denominators and scoped `User.participating` are determined by `ChallengeMembership.status='active'`. The roster endpoint `/teacher/students` remains account-wide; `targetType` is the roster's required/optional classification. Creating a required student or changing that classification does not enroll them in a challenge; the challenge's forced-registration action does that. The existing account-wide `User.participating` flag is retained for legacy compatibility and is not the authority for challenge membership.

Challenge errors use the standard `{error:{code,message,details?}}` envelope: `400 INVALID_CHALLENGE` includes `details:[{path,message}]`; `404 CHALLENGE_NOT_FOUND`; `409 CHALLENGE_LOCKED`, `CHALLENGE_ARCHIVED`, `CHALLENGE_NOT_DRAFT`, `ALREADY_PUBLISHED` and `CHALLENGE_NOT_PUBLISHED`. Explicit challenge record access and record mutations without an active membership return `403 NOT_MEMBER`; the legacy empty-read compatibility above is retained. Membership errors include `400 INVALID_SELECTION`, `409 ENROLLMENT_CLOSED`, `409 INVITATION_CLOSED`, `404 NO_INVITATION`, `409 INVITATION_SELECTION_REQUIRED` and `409 HAS_RECORDS`.

## Challenge memberships (teacher)

`Membership = {id,challengeId,user:User,mode,status,invitedAt,respondedAt:null|ISO,invitedBy:null|{id,name}}`. `mode` is `forced|invited`; `status` is `active|pending|declined|removed`. An absent inviter is retained as null for legacy migration without a teacher or a deleted inviter. New teacher actions identify the acting teacher. Membership and preview `User.participating` reflect active membership in this challenge; `targetType`, grade and class remain roster classifications. Account-wide `/teacher/students` and `/auth/me` retain the legacy account value. `MembershipSelf = {mode,status,invitedAt,respondedAt}` contains no other user's identity.

- `GET /teacher/challenges/:id/members?status=&mode=&grade=&classNumber=&targetType=&search=` → `{members:[Membership],stats:{active,pending,declined,removed,forced,invited}}`. Default statuses are `active,pending,declined`; removed rows stay stored but are hidden by default. Grade/class/target/search define the statistics cohort; status/mode filter only the member list. Mode totals exclude removed memberships.
- `POST /teacher/challenges/:id/members/preview {studentIds?:[id],filters?:{grade?,classNumber?,targetType?,fitnessGrades?:[1,2,3,4,5]}}` → `{students:[User & {membership:null|MembershipSelf}]}`. Supply exactly one selector. `fitnessGrades` is a nonempty array of integers 1–5 (duplicates collapse), selects the union of those grades and intersects other filters; unknown grades are excluded. An empty `filters:{}` explicitly selects all students. The same selector works for member creation, and member list queries accept singular `fitnessGrade` as above. Preview writes no memberships or notifications. Invalid selection or selection input exceeding 100,000 characters returns `400 INVALID_SELECTION`.
- `POST /teacher/challenges/:id/members {mode:'forced'|'invited',studentIds?:[id],filters?:{grade?,classNumber?,targetType?}}` → `201 {added:[Membership],skipped:[{userId,studentNumber,name,reason}]}`. The complete selection is applied atomically. Only published challenges accept registration. Forced registration remains available through `endDate`; sending an invitation remains available through `enrollmentDeadline`, including the deadline's Korean calendar date.
- `DELETE /teacher/challenges/:id/members/:userId` → `{ok:true}`. Sets `status='removed'` without deleting the membership. A record in that challenge prevents removal with `409 HAS_RECORDS`; records belonging only to another challenge do not prevent it. An absent membership returns `404 NOT_MEMBER`.

Forced registration creates `forced/active`; invitation creates `invited/pending`. A pending invite may become `forced/active`; reinviting a pending member skips them with `already_pending`. A declined member may be reinvited or forced, and a removed member may be registered again using the same row. Existing active members are skipped with `already_active`. Missing IDs and teacher IDs are skipped as `not_found` and `not_student`. The roster's required/optional classification and account fields are not changed by these operations.

Only active memberships permit record access/mutations and enter performance denominators. Pending, declined and removed memberships are excluded. Responses to invitations change only the selected challenge's membership. Concurrent accept/decline, registration/removal and record writes cannot silently overwrite a competing state change.

## Student challenge endpoints

- `GET /student/challenges` → `{current:null|{challenge:ChallengeSummary,membership:MembershipSelf},challenges:[{challenge,membership}],invitations:[{challenge,membership}],closedInvitations:[{challenge,membership}],archived:[{challenge,membership}]}`. All challenge entries use `ChallengeSummary`; invitations contain pending invitations to published challenges that are still within their enrollment deadline. Current-challenge priority matches the legacy resolver above. `closedInvitations` lists pending invitations whose `enrollmentDeadline` has passed while the challenge has not yet ended (today ≤ `endDate`), so the student can see why they cannot join; accepting them still returns `409 INVITATION_CLOSED`. `archived` lists archived challenges the student was an active member of; they are never current, their detail/dashboard/records stay readable, and record/correction/attachment writes return `409 CHALLENGE_ARCHIVED`.
- `POST /student/challenges/:id/accept {}` → `{membership:MembershipSelf}`. Only the student's pending invitation can become active, through `enrollmentDeadline` inclusive. No pending invitation returns `404 NO_INVITATION`; a missed acceptance deadline returns `409 INVITATION_CLOSED`.
- `POST /student/challenges/:id/decline {}` → `{membership:MembershipSelf}`. Only a pending invitation may become declined; forced or already-active membership cannot be declined. No pending invitation returns `404 NO_INVITATION`.
- `GET /student/challenges/:id` → `{challenge:Challenge}`. The full challenge includes `weeks` and `activityDates`. Published details are available to authenticated students even before accepting an invitation. Draft and archived details are not student-visible.
- `GET /student/challenges/:id/dashboard` → `{user,challenge:Challenge,membership:MembershipSelf,summary,records,unreadCount}`. Requires an active membership; record arrays and summaries belong only to this challenge. Notifications and unread count remain account-wide.
- `GET /student/challenges/:id/records`, `GET /student/challenges/:id/records/:date`, `PUT /student/challenges/:id/records/:date`, and `POST /student/challenges/:id/records/:date/corrections` share the legacy handlers and response shapes described below, with an explicit challenge instead of the current challenge.
- `POST /student/challenges/:id/records/:date/attachments` and `DELETE /student/challenges/:id/records/:date/attachments/:id` use the same private storage, upload limits and current-day policy as the legacy attachment routes. The record must belong to both the student and this challenge.

Record, correction and attachment writes recheck the published lifecycle and active membership inside their database transaction, with row locks shared with registration/removal/archive operations. An upload that started on an allowed activity day may finish after midnight, but completing it cannot bypass a newly archived challenge or a removed membership. A failed upload leaves the saved numeric record intact and removes its uncommitted file.

## Student (legacy current-challenge paths, deprecated)

`GET /program`, `GET /student/dashboard`, `GET /student/records*` and `POST /student/enroll` stay for one release and answer with `Deprecation: true`; they will be removed in the next release. Clients use the `/student/challenges/:id/...` paths above. Record/correction/attachment writes under `/student/records/:date` share the same handlers.

- `GET /program` → `{challengeId,year,today,status,startDate,endDate,weeks,activityDates,week12Pending}` using `programDto(challenge)`; no current challenge returns `404 CHALLENGE_NOT_FOUND`. The previous response fields remain, and year/dates/week count come from the selected challenge. Week definitions contain `week,title,startDate,endDate,inputType,weeklyTarget,dailyTarget,unit,dailyUnit,color,description`; dumbbell weeks expose `exercises:[{id,title,repetitions,targetSets,sideRule}]`. `week12Pending` remains false for the settled legacy challenge.
- `GET /student/dashboard` → `{user,program,summary,records,unreadCount}`. Summary `{weeks,completedWeeks,totalWeeks,pendingWeeks,complete,progress,status}`. Week summary includes `week,weekdayTotal,weekendTotal,total,weekdayAchieved,weekendAchieved,makeupDays,complete,progress,status,recordedDays`.
- `POST /student/enroll {}` → `{user}` remains a legacy compatibility path. It finds the student's `invited/pending` invitations to published challenges whose deadline includes today, independently of the active-only current-challenge resolver. Zero eligible invitations returns the existing `403 ENROLLMENT_CLOSED`; exactly one accepts it and returns the user with participating true. Multiple eligible invitations change nothing and return `409 INVITATION_SELECTION_REQUIRED` with `details:{challengeIds:[id,...]}` so the client can request a choice and call `POST /student/challenges/:id/accept`.
- `GET /student/records` → `{records,summary}`.
- `GET /student/records/:date` → `{record:null|Record,corrections,week,dailyStatus,editable}`.
- `PUT /student/records/:date {value,version?}` → `{record,summary}`. Same Korea date only, participating students, active date. Existing record requires `version` (optimistic conflict check). Never sums with the previous value.
- `POST /student/records/:date/corrections {value,reason,version}` → `{correction}`. Existing past record only, one pending request; leaves effective value unchanged.
- `GET /student/corrections` → `{corrections}`. Correction includes `{id,challengeId,recordId,date,beforeValue,requestedValue,reason,status,decisionReason,createdAt,decidedAt}`; this list remains account-wide.
- `GET /student/notifications` → `{notifications,unreadCount}`. Notification `{id,type,title,body,data,readAt,createdAt}`; `data` is null for reminder/correction events and is `{challengeId,membershipId}` for invitation/enrollment events.
- `POST /student/notifications/:id/read {}` → `{ok:true}`.
- `POST /student/notifications/read-all {}` → `{ok:true}`.
- `GET /student/settings` → `{weekendReminder,pushEnabled,pushPublicKey}`.
- `PATCH /student/settings {weekendReminder}` → same settings.
- `POST /student/push-subscriptions {endpoint,keys:{p256dh,auth}}` → `{ok:true}`. Binds the owned subscription to this browser device and authenticated session. An endpoint owned by another account returns 409.
- `POST /student/push-subscriptions/status {endpoint}` → `{registered:boolean}`. True only when this exact endpoint belongs to the authenticated student; an owned endpoint is also bound to this browser device/session. No other account details are returned. Browser permission alone does not establish account ownership. Both binding endpoints revalidate and lock the current session so requests already in flight cannot restore a binding after logout or account switch.
- `DELETE /student/push-subscriptions {endpoint}` → `{ok:true}`.
- `POST /student/records/:date/attachments` multipart field `file` → `{attachment}`. Record must already exist. Images max 3×10MB, video max 1×100MB/60 seconds; same-day start. Numeric record is preserved on upload failure.
- `DELETE /student/records/:date/attachments/:id` → `{ok:true}`. Same-day only.
- `GET /attachments/:id` → private file; owner student or teacher only. File `url` points here.

## Teacher

Common filters: `search,grade,classNumber,targetType,participating` (active in the selected challenge)`,achievement` (`complete|incomplete|pending`), `week` (1..20, must exist in the selected challenge), `studentIds` (comma-separated IDs). Students without an active membership remain roster members but do not enter that challenge's performance denominator.

- `GET /teacher/overview?filters` → `{students:[User & {summary,records}],challenge,program,stats:{students,participants,completed,denominator},filters}`. School roster with records and summaries scoped to the chosen challenge (82 dates for the legacy challenge), no synthetic rows.
- `GET /teacher/participation?grade=&classNumber=&targetType=` → `{challenge,summary,weeks,grades,classes,targets,filters,filterOptions}`. Only active memberships in the selected challenge enter the cohort. Summary/group `completionRate` is `completedWeeks/(participants*totalWeeks)*100`; weekly rate is completed students/participants*100. Rates are unrounded 0–100, null for empty cohorts. Summary includes `participants,completedWeeks,possibleWeeks,totalWeeks,pendingWeeks`; groups include identity/label and the same counts. `filterOptions` contains all registered student grades/classes independently of the active filters. No student identity or individual records are returned.
- `GET /teacher/students?filters&challengeId=` → `{students:[User]}`. Account-wide roster. `participating` (and the `participating` filter) is an active membership in `challengeId`, or in the teacher's current challenge when omitted (false when there is none); unknown IDs return `404 CHALLENGE_NOT_FOUND`.
- `POST /teacher/students {studentNumber,name,grade,classNumber,targetType}` → `{user,temporaryPassword}`. Password returned once only. Creating (or importing) a student does not enroll them in any challenge; teachers register or invite them per challenge. Existing student number → 409 `DUPLICATE_NUMBER`.
- `PATCH /teacher/students/:id {studentNumber?,name?,grade?,classNumber?,targetType?}` → `{user}`. Updates the account-wide roster classification; challenge participation is determined by its active membership. No deletion of records.
- `DELETE /teacher/students/:id` → `{ok:true}`. Only accounts without records/corrections can be deleted; otherwise 409 preserving evidence.
- `GET /teacher/students/:id` → `{challenge,user,records,summary,corrections,fitnessHistory}`.
- `POST /teacher/students/:id/reset-password {}` → `{temporaryPassword}`; revokes all existing student sessions.
- `GET /teacher/roster/template` → XLSX with headers `학번,이름,학년,반,대상구분` and no fake students.
- `POST /teacher/roster/validate` multipart `file` (.xlsx, max 5MB) → `{importId,rows:[{studentNumber,name,grade,classNumber,targetType}],errors:[{row,message}],expiresAt}`. Strict validation, no writes. target labels `필수|선택` (or required|optional). Duplicates/existing student numbers are errors. Import expires after 30 min.
- `POST /teacher/roster/commit {importId}` → `{created,credentials:[{studentNumber,name,temporaryPassword}]}`. Atomic, consumes validated import exactly once. Save passwords locally at this response; they cannot be retrieved again.
- `GET /teacher/corrections?status=pending|approved|rejected|all` → `{challenge,corrections}` including student identity and current Record. A pending request with a matching current record version includes `preview:{before:WeekSummary,after:WeekSummary}`; stale/decided requests have `preview:null`. Preview never writes data.
- `GET /teacher/corrections/export?status=all|pending|approved|rejected` → XLSX correction audit history, including original/requested values, reasons, requester, teacher, status and Korea timestamps. This is separate from current effective activity export.
- `POST /teacher/corrections/:id/approve {}` → `{correction,record}`. Atomic version check; stale request gets 409 and never overwrites current record. A request on an archived challenge's record gets `409 CHALLENGE_ARCHIVED` (it can still be rejected).
- `POST /teacher/corrections/:id/reject {reason}` → `{correction}`. Nonempty reason required.
- `GET /teacher/export?filters` → XLSX sheets summary, weekly, daily, dumbbell details, metadata. Dumbbell detail preserves each exercise's set count, missing vs zero, target, converted repetitions and side rule. Current effective values; no original media embedded. Week filter narrows weekly/daily/dumbbell sheets, summary retains the whole selected challenge's meaning.

## Runtime

`DATABASE_URL`, `APP_ORIGIN` (default http://localhost:5173), `PORT` (4000), `HOST` (127.0.0.1), `STORAGE_DIR` private absolute path, `FFPROBE_PATH` optional, `TRUST_PROXY` optional (Express trust-proxy value behind a reverse proxy), `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` optional. Push configuration absence never blocks app notifications. Reminder scheduler runs each minute, Korea 20:00 onwards, separately for published challenges whose phase is active. Active membership and that challenge's weeks determine eligibility; event key `reminder:<challengeId>:<userId>:<date>` prevents duplicates within each challenge. It never sends exercise reminders beyond that challenge's endDate. Existing pre-migration reminder keys remain history and are not sent again. No automatic data/media deletion policy.

Immediately before each reminder push (including retries), the server rechecks the current Korea date, same-day challenge/event identity, published lifecycle, active membership, weekly completion, daily input and weekend setting. Obsolete reminder pushes become `cancelled`; their in-app event history remains. Invitation, forced-enrollment and correction-result pushes bypass the exercise-reminder eligibility gate, so an upcoming challenge or a completed activity does not suppress them. Invitation creation/reinvitation emits `type:'invitation'`, title `새 챌린지에 초대됐어요`, body including the challenge title and deadline, and event key `invitation:<membershipId>:<invitedAt ISO>`. Forced enrollment emits `type:'enrollment'` with event key `enrollment:<membershipId>`. Both carry `data:{challengeId,membershipId}`. Repeated active registration creates no new event; forced reenrollment of a removed row retains its one existing enrollment event. Push payloads include this data and use `/mobile/challenges` as their click URL when `data.challengeId` is present; other events use `/mobile/notifications`. The existing frontend service worker currently opens `/mobile/notifications` regardless of the payload URL. Consuming the challenge URL and connecting the challenge screens remain frontend integration work; backend transport tests verify the payload only.

Before each device send, the server also rechecks subscription identity and ownership so a queued snapshot cannot send to a device already revoked by logout or removal.

Push registration and owned-status checks set `self_fit_push_device` when needed: a random 32-byte, HttpOnly, SameSite=Lax cookie scoped to `/api`, Secure in production, with a one-year lifetime. Only its SHA-256 hash is stored on the subscription and session; no device identifier is exposed in API JSON. The session copy supports logout before a new cookie response reaches the browser. Logout preserves the device cookie for later account switches; a cookie with no registered subscription has no effect.

Initialize schema `npm run db:deploy`, then run `npm run bootstrap-teacher` in a terminal to enter the one real teacher's ID, name and hidden password. `TEACHER_ID`, `TEACHER_NAME`, and `TEACHER_PASSWORD` env or stdin JSON are also supported. Backend reads `backend/.env`. Never pass passwords on CLI args. No seed users or activity are installed.

## 교사 학생 비밀번호 관리

- 기존 User.mustChangePassword가 true이면 학생 비밀번호 변경 필요, false이면 변경 완료입니다.
- GET /teacher/students/:id/password-status → {changed:boolean, changedAt:ISO|null, issuedAt:ISO|null, temporaryPasswordAvailable:boolean}. 교사 전용이며 비밀번호 원문은 포함하지 않습니다. 기존 변경 시각을 추정하지 않습니다.
- GET /teacher/students/:id/temporary-password → {temporaryPassword:string}. 교사만 현재 유효한 초기/임시 비밀번호를 명시적으로 조회합니다. 학생이 변경했거나 보존본이 없으면 409 TEMPORARY_PASSWORD_UNAVAILABLE입니다. 모든 응답은 Cache-Control: no-store입니다.
- POST /teacher/students/:id/reset-password는 기존 {temporaryPassword} 계약을 유지합니다. 새 임시 비밀번호를 암호화해 보관하고 모든 기존 학생 세션을 종료하며 변경 필요 상태로 만듭니다.
- 학생 개별 생성·엑셀 등록도 임시 비밀번호를 암호화해 보관합니다. 학생 비밀번호 변경 시 보관본을 제거합니다. 학생이 직접 정한 비밀번호는 조회할 수 없습니다.
- 서버 TEMPORARY_PASSWORD_KEY는 32바이트 키의 64자리 hex 값입니다. DB와 분리해 보관합니다. 키가 없거나 잘못되면 발급/조회는 503 PASSWORD_VAULT_UNAVAILABLE이며 DB를 변경하지 않습니다. 잘못된 키로 기존 보관본을 읽으려 해도 동일 오류입니다.
- 기존 계정은 현재 해시와 일치하는 초기 비밀번호의 비공개 원본이 있을 때만 보완합니다. 비밀번호 변경·계정 초기화는 보완 작업에서 하지 않습니다.

서버 시작 시 환경 키가 없으면 `TEMPORARY_PASSWORD_KEY_FILE` 또는 비공개 `STORAGE_DIR/.secrets/temporary-password.key`에 키를 최초 1회 생성하고 재사용합니다. 운영 서버의 기존 영속 저장소·systemd 쓰기 권한과 호환됩니다. 원본 키 파일은 DB와 별도로 비공개 백업합니다.
